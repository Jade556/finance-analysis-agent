## 〇、先看懂一次请求怎么在系统里流动

### 场景 A：用户问"昨天抖音渠道亏损了吗？"

```
浏览器输入问题
  → frontend.html 发 POST /api/chat  (body: {message})
    → main.py: chat_endpoint 打开一个 SSE 流 (StreamingResponse)
      → agent_app.astream_events(...) 驱动 LangGraph 逐事件执行
        → graph.py: reasoner 节点 (LLM 带着 8 个工具做推理)
           判断需要数据 → 产出 tool_calls
        → tools 节点 (ToolNode) 执行 get_douyin_campaign_data 等工具
           工具结果回传
        → reasoner 再次推理，可能再调工具（多步），直到不再需要工具
      → 每一步都通过 SSE 推给前端：
         on_chat_model_stream → {type:'token'}      (正文逐字)
         on_tool_start        → {type:'tool_start'} (思维链：调了什么工具)
         on_tool_end          → {type:'tool_end'}   (思维链：工具返回了什么)
      → 结束发 [DONE]
  → 前端边收边渲染：正文用 marked 渲染成 Markdown，工具调用显示在"思维链"侧栏
```

**一句话**：`reasoner`（大脑）和 `tools`（手）反复来回，就是 ReAct 循环；LangGraph 负责这个来回的编排和状态管理，FastAPI 负责把过程流式推给前端。

### 场景 B：用户问"库存低于2万的商品有哪些？"（触发 Text2SQL）

```
reasoner 判断固定工具不够灵活 → 调 query_erp_by_natural_language(question)
  → tools.py 里这个工具调用 app/text2sql.py: text2sql()
    → get_schema()  自省 ERP 库结构 + 采样几行，拼进 prompt
    → LLM 生成 SQL
    → is_safe_select() 只读安全校验
    → run_sql() 执行；若报错 → 把错误回灌 LLM 重新生成（最多3轮）
    → 成功 → 返回 rows
  → 结果回到 reasoner，组织成自然语言 + 表格回答
```

## 一、app/graph.py —— Agent 的骨架（LangGraph 状态图）

这是整个 Agent 的**编排中枢**。

### 1) 状态定义 `AgentState`
```python
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
```
- `messages` 是对话历史（人类消息、AI 消息、工具消息都在里面）。
- `Annotated[list, add_messages]`：`add_messages` 是 LangGraph 的 **reducer（归约器）**。它规定"当某个节点返回新的 messages 时，是 **追加** 到历史，而不是覆盖"。这就是为什么 reasoner 每次 `return {"messages": [response]}` 只返回**一条**，历史却越积越全。
- 面试点：为什么要 reducer？因为图里多个节点都会写 `messages`，没有归约策略就会互相覆盖。

### 2) 工具清单 `tools`（8 个）
把 `tools.py` 里的 8 个工具收成一个列表，传给两个地方：
- `llm.bind_tools(tools)`：让 LLM **知道**有哪些工具、每个工具的参数长什么样（靠工具的类型注解 + docstring 生成 JSON schema）。
- `ToolNode(tools)`：真正**执行**工具的节点。

### 3) LLM 构造
```python
llm = get_llm(temperature=0, timeout=120)
llm_with_tools = llm.bind_tools(tools)
```
- `temperature=0`：财务场景要稳定、可复现，不要发散。
- `get_llm` 来自 `llm_factory.py`（见后），统一读环境变量。

### 4) `reasoner` 节点（大脑）
```python
def reasoner(state):
    prompt = ChatPromptTemplate.from_messages([("system", system_prompt), MessagesPlaceholder("messages")])
    chain = prompt | llm_with_tools
    response = chain.invoke({"messages": state["messages"]})
    return {"messages": [response]}
```
- `system_prompt` 是一大段"人设 + 规则"，重点几条：
  - **数据日期锚定**：告诉它"昨天=2025-10-20"，避免它瞎猜日期（LLM 不知道今天几号）。
  - **禁止心算利润**：必须调 `calculate_sku_net_profit`（**去幻觉**，数值计算不能信 LLM）。
  - **人机协同格式**：发工单必须输出 `[CONFIRM_ACTION]...[/CONFIRM_ACTION]` 这个精确结构，前端才能解析成"确认卡片"。
- `prompt | llm_with_tools` 是 LangChain 的**管道语法**：把 prompt 模板和带工具的 LLM 串成一条链。
- 返回的 `response` 可能包含 `tool_calls`（要调工具）或纯文本（直接答）。

### 5) 图的结构（节点 + 边）
```python
builder.add_node("reasoner", reasoner)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "reasoner")            # 入口 → 大脑
builder.add_conditional_edges("reasoner", tools_condition)  # 大脑后分叉
builder.add_edge("tools", "reasoner")          # 工具执行完 → 回大脑
```
- **`tools_condition`**（官方内置的条件函数）：检查 reasoner 的输出里有没有 `tool_calls`。
  - 有 → 去 `tools` 节点执行；
  - 没有 → 去 `END`（把最终答案返回）。
- `tools → reasoner` 这条回边，就是"工具结果回传给大脑解读"，构成 ReAct 闭环。

### 6) 编译 + 记忆
```python
memory = MemorySaver()
graph = builder.compile(checkpointer=memory)
agent_app = graph
```
- `MemorySaver`：把对话状态按 `thread_id` 存在内存里，实现多轮记忆（同一 thread 的第二次提问能记得上文）。生产环境会换成 Redis/DB 的 checkpointer。
- `interrupt_before=["tools"]`（注释掉的）：LangGraph 原生的人机协同——执行工具前**暂停**等人工确认。本项目目前用 prompt 里的 `[CONFIRM_ACTION]` 协议实现同样效果（面试可讲两种做法的取舍）。

## 二、app/tools.py —— 8 个工具（Agent 的"手”）

每个工具都用 `@tool` 装饰。**docstring 极其重要**——它会被喂给 LLM，决定 LLM 什么时候选这个工具、怎么填参数。所以每个 docstring 都写清了"什么场景用、参数、返回"。

| 工具 | 数据源 | 干什么 |
|---|---|---|
| `get_tmall_sales_data` | tmall_data.json | 按日期/SKU 过滤天猫销售明细 |
| `get_douyin_campaign_data` ★加了 `@resilient(cache_ttl=30)` | douyin_data.json | 汇总抖音 GMV/广告费/退款/退货率等 |
| `get_xiaohongshu_sales_data` ★新增 | xiaohongshu_raw.csv | 清洗脏 CSV 后返回小红书汇总 |
| `list_available_skus` | erp.db | 列出所有 SKU（供 LLM 先查再用） |
| `get_product_cost_structure` | erp.db | 查单个 SKU 的成本与库存 |
| `query_erp_by_natural_language` ★新增 | erp.db | Text2SQL：自然语言即席查询 |
| `calculate_sku_net_profit` | 纯计算 | 严谨核算净利润（去幻觉） |
| `create_feishu_ticket` | 副作用 | 发工单（人机协同确认后才调） |

### 逐个要点
- **`get_douyin_campaign_data`**：读 JSON → pandas 过滤日期 → 从嵌套字段 `cost_structure`/`after_sales` 里抽广告费、退款，算出 `return_rate`、`ad_fee_ratio` 等。★我给它加了 `@resilient(cache_ttl=30)`，同参数 30 秒内直接走缓存。
- **`calculate_sku_net_profit`**：纯 Python 加减。刻意做成工具是因为**LLM 心算会出错**，把数值计算交给确定性代码。公式：`净利 = GMV - (广告费+佣金+平台费+总COGS+总物流+退款)`。
- **`create_feishu_ticket`**：目前只 `print` 模拟（真实环境接飞书/企业微信 API）。是唯一有"副作用"的工具，所以走人机协同。
- **★`query_erp_by_natural_language(question)`**：函数体很薄——`from app.text2sql import text2sql` 然后调用，把结果精简后返回给 LLM。真正的逻辑在 text2sql.py。（延迟导入是为了让不涉及 LLM 的测试能单独跑）
- **★`get_xiaohongshu_sales_data(start,end)`**：调 `ingest.load_and_clean()` 拿清洗后的记录，按日期过滤后聚合成 summary，并把 `clean_report` 一起返回（让"清洗过程"可见）。也加了 `@resilient(cache_ttl=60)`。

## 三、★app/text2sql.py —— Text2SQL 引擎（核心卖点）

把"自然语言→SQL→执行→出错自纠"整条链路收进来。分 5 块：

### 1) `get_schema()` —— schema linking
- 用 `sqlite_master` 查出所有表，对每张表取 DDL（建表语句）+ `PRAGMA table_info` 拿列名 + `SELECT ... LIMIT 3` 采样几行真实数据。
- 拼成一段文本喂给 LLM。**为什么带样例数据**：让模型看到"库存是整数、成本是小数、sku_id 长这样"，减少字段猜错。
- **为什么不硬编码 schema**：这样换库/加表都不用改代码，`get_schema` 自动反映最新结构（可扩展）。

### 2) `is_safe_select(sql)` —— 只读安全闸
- 三道校验：① 不能有 `;`（防多语句注入）；② 用正则黑名单拦 `insert/update/delete/drop/alter/...`；③ 必须以 `select` 或 `with` 开头。
- **为什么**：数据分析 Agent 绝不允许改库；LLM 生成的 SQL 是不可信输入，必须校验。

### 3) `_clean_sql(raw)`
- 剥掉 LLM 可能输出的 ```` ```sql ... ``` ```` 代码块围栏，只留纯 SQL。

### 4) `run_sql(sql)` ★带 `@resilient`
- 先过安全闸，再 `sqlite3` 只读执行，用 `row_factory = sqlite3.Row` 把结果转成 dict 列表。
- **关键**：出错时不抛异常，而是返回 `{"ok": False, "error": "SQLite 执行错误: ..."}`——**把 sqlite 的原始报错带回去**，这是自纠环能工作的前提。

### 5) `text2sql(question, max_retries=3, llm=None)` —— 自纠环
```
for attempt in 1..max_retries:
    prompt = 模板.format(schema, question, feedback)
    sql = clean(llm.invoke(prompt))
    result = run_sql(sql)
    记 trace
    if result.ok: return 成功
    else: feedback = "上一轮SQL执行失败，错误是...请修正"   # 回灌错误
return 失败
```
- **自纠核心**：每轮把上一轮的**错误 SQL + 报错信息**拼进 prompt，让模型带着反馈重生成。这就是"执行反馈自纠环"。
- **`llm=None` 参数**（★依赖注入）：正常运行时内部 `get_llm()`；测试时可注入一个"先错后对"的桩 LLM，**确定性验证自纠环**（见 eval/test_self_correction.py）。
- 返回里带 `trace`（每轮的 SQL 和成败），前端思维链和评测归因都能用。

## 四、★app/ingest.py —— 异构脏数据清洗

处理小红书那份**故意做脏**的 CSV（`data/xiaohongshu_raw.csv`）。

`load_and_clean(path)` 的流水线（★带 `@resilient`）：
1. **容错读取**：`pd.read_csv(engine="python", on_bad_lines="skip")`，坏行（列数不齐）跳过并计数 `bad_lines_skipped`，不让整个管道崩。
2. **表头规范化**：`_norm_header` 把 `" gmv(元) "` 这种带空格/大小写乱的表头，通过 `_HEADER_MAP` 映射成规范字段名 `gmv`。
3. **逐列清洗**：
   - `_parse_date`：把 `2025/10/20`、`2025-10-20`、`2025.10.20`、`20251020` 四种格式统一成 `YYYY-MM-DD`（先抽数字再拼）。
   - `sku_id`：去空格 + 转小写（`" SKU_CAT_002 "` → `sku_cat_002`）。
   - `_parse_money`：剥掉 `¥`、千分位逗号、空格；`N/A`/`-`/空 识别成缺失(None)。
4. **去重**：`drop_duplicates()`，计 `dropped_duplicates`。
5. **丢关键缺失**：日期/sku/gmv 任一缺失的行丢掉，计 `dropped_key_missing`；退款缺失按 0 兜底，计 `refund_filled_zero`。
- 最后返回 `records`（规范数据）+ `clean_report`（每一步做了什么，**可解释**）。
- 面试点：为什么把清洗报告也返回？让"数据质量处理"可见、可审计，而不是黑箱。

## 五、★app/resilience.py —— 工具韧性层

一个装饰器 `@resilient(retries, backoff, timeout, cache_ttl)`，给任意工具函数套上三件套：

- **TTL 缓存**：用"函数名+入参"做 key（`_make_key`，JSON 序列化），命中且未过期就直接返回，省重复 IO。
- **超时**：用 `ThreadPoolExecutor.submit(...).result(timeout=...)` 实现。**为什么用线程池不用 signal**：`signal.SIGALRM` 只能在主线程用、且 Windows 不支持；线程池方案跨平台。
- **重试 + 指数退避**：失败后等 `backoff * 2^n` 秒再试，最多 `retries` 次。
- **兜底不抛异常**：重试耗尽返回 `{"error": ...}`，把决策权交回给 reasoner（它可以换个工具或告诉用户），避免一次抖动打断整条推理链。
- `cache_stats()`：给 `/api/health` 用，报当前缓存了多少 key。

## 七、app/main.py —— FastAPI 服务层

- **★UTF-8 兜底**（文件顶部）：把 `sys.stdout/stderr` 重设为 UTF-8，否则 Windows GBK 控制台遇到中文/emoji 日志会 `UnicodeEncodeError` 崩溃。
- **CORS + 静态挂载**：开发期放开跨域；`/static` 挂载项目目录。
- **端点**：
  - `GET /` → 返回 `frontend.html`。
  - **★`GET /api/health`** → 数据源存在性 + 工具缓存概览（可观测性）。
  - `POST /api/chat` → **核心**。`astream_events(version="v1")` 逐事件驱动图，把三类事件转成 SSE：
    - `on_chat_model_stream` → `{type:token}`（正文逐字流）
    - `on_tool_start` → `{type:tool_start}`（思维链：调了哪个工具、参数）
    - `on_tool_end` → `{type:tool_end}`（思维链：工具返回）
    - 整个生成包在 try/except 里，出错发 `{type:error}`，最后必发 `[DONE]`。
  - `GET /api/scan-alerts` → 用**业务规则**扫数据出预警（广告费占比>25% 或退货率>25% → 利润预警；库存<阈值 → 库存预警）。这是首页"主动预警"卡片的数据源。
  - `GET /api/data-preview` → 给首页"数据源"面板返回抖音/ERP 的样例数据。
- **★`kill_port`（跨平台）**：启动前释放 8000 端口。基座原来只有 Mac 的 `lsof`，我加了 Windows 的 `netstat + taskkill` 分支。

## 九、eval/ —— 评测体系（把"改进"变成数字）

- **`eval_set.json`**：Agent 工具选择评测集。每条 `must_call` 列可接受的工具，`match:any/all` 决定判定方式。
- **`run_eval.py`**：
  - `extract_called_tools(messages)`：从返回消息里抽出所有被调工具名。
  - `run()`：逐条 `agent_app.invoke` 跑真实 Agent，比对是否命中期望工具 → 算**工具选择准确率**。
  - `run_text2sql_eval()`：读 `text2sql_questions.json`，直接调 `text2sql()` 跑每道题 → 算**Text2SQL 执行成功率 + 平均自纠轮次**（隔离于 Agent 的工具选择）。
- **`text2sql_questions.json`**：Text2SQL 直测题库，含多表 JOIN、CTE、聚合。
- **★`test_self_correction.py`**：**离线确定性**测试。用 `StubLLM` 第 1 轮吐会报"ambiguous column"的坏 SQL、第 2 轮吐加了表前缀的正确 SQL，断言 `attempts==2 且最终成功`——不依赖真实 LLM，证明自纠环真能恢复失败。
